# Spherewright CommandDeck

A desktop workspace for playing Dyson Sphere Program with a structured Agent and for developing and validating Spherewright.

**Status: M1 development and main-window docking/layout restoration have validation evidence. M2 has completed finite real shared-panel/RPC observations, connection-only UI timing and bounded reader shutdown in a dedicated idle world; loaded-factory overhead, multiple worlds and long-run evidence remain open. M3 has completed one real MiniMax → native confirmation → ordinary DSP research enqueue → original-action/queue readback → normal-save workflow. M4 has completed its first finite source → checks/CI → Lab → cold installation/recovery → basic live display → persistent diff/log/evidence navigation workflow. Native input coordination and real failure coverage remain open. The owner has deferred the unresponsive embedded DSP menu; this behavior is not an input lock.**

Implementation stages, dependencies and acceptance gates are tracked in [ROADMAP.md](ROADMAP.md) (Chinese). The 0.1.0 plan includes both a directly interactive native game viewport and a development workflow across Spherewright and Lab.

## Repository boundaries

| Repository | Responsibility |
| --- | --- |
| [Spherewright](https://github.com/Arcueid77/Spherewright) | Game Plugin, local Bridge, MCP contracts, native observations and controlled actions. |
| [Spherewright-Lab](https://github.com/Arcueid77/Spherewright-Lab) | Scenarios, acceptance evidence and version locks across the product repositories. |
| [Spherewright-CommandDeck](https://github.com/Arcueid77/Spherewright-CommandDeck) | Desktop UI, native game-window host, development workspaces, task permissions and the game-action ledger. |
| [Spherewright-Pi](https://github.com/Arcueid77/Spherewright-Pi) | Source fork of the Pi Agent runtime, included here as the vendor/pi submodule. |

Lab belongs in a Spherewright **development workspace**, alongside the game-control source and CommandDeck. It is an independent repository and is not a required dependency of the CommandDeck application build or installed runtime. Existing checkouts can stay in their current locations; the workspace UI supports multiple explicitly authorized roots.

Conceptual layout, rather than a requirement to move existing repositories:

~~~text
Development workspace
  Spherewright/                 game-control source
  Spherewright-Lab/             scenarios and acceptance evidence
  Spherewright-CommandDeck/     desktop application source
    vendor/pi/                  Spherewright-Pi Git submodule
~~~

## Pi source dependency

The fork preserves the complete upstream monorepo and its license notices. Upstream is [earendil-works/pi](https://github.com/earendil-works/pi), formerly badlogic/pi-mono.

The initial submodule baseline is upstream v1.3.0, commit 71023aec1546d6d677a65669c5665c0927ce0dd0. The parent repository pins an exact commit; it does not automatically follow the fork's default branch. Future CommandDeck releases must record both the application commit and the Pi submodule commit.

Clone with the pinned dependency:

~~~powershell
git clone --recurse-submodules https://github.com/Arcueid77/Spherewright-CommandDeck.git
~~~

For an existing checkout:

~~~powershell
git submodule update --init --recursive
~~~

Changes to Pi are committed and pushed in Spherewright-Pi first. CommandDeck then records the new submodule commit in a separate integration change. Check out an explicit development branch before editing the submodule; an ordinary submodule checkout is detached.

The prototype imports the built coding-agent entry directly from the submodule. `pi:verify` checks the exact commit, compiled entries and internal workspace links. Pi source is unchanged at this baseline. Its ignored model catalog is restored from the matching versioned npm artifact using the integrity in `pi-model-data-lock.json`; only JSON catalog data is copied, not registry runtime modules. End-user packaging remains a later milestone.

## Diagnostic reports (M5)

Open **诊断报告** in the header, choose task/event summaries and cached performance data, then select **生成预览**. The complete JSON shown there is the exact content offered for saving. The native save picker selects a new `.json` file; cancelling preserves the same preview, while existing files and the application's installation/private-profile directories are refused. A preview expires after five minutes and is invalidated by changed options, UI reload or replacement. An accepted write may finish during shutdown; a failed or unconfirmed write may leave an incomplete new file and is never automatically retried.

Reports contain bounded structural task/event/error records, package-reported source pins and cached numeric metrics. They omit credentials, approval tokens, private paths, world/session/action identities, prompts, model responses, command arguments and output. Task labels exist only within one report. Missing, unsupported and truncated data remain explicit; source builds do not invent a verified revision, and package metadata is not a signature or a full installation integrity check. Generating a report does not start a model, refresh MCP or query the game. Reports are informational and cannot be replayed as actions.

```powershell
npm run test:diagnostics
npm run test:packaged-diagnostics -- --source artifacts/portable-desktop
```

## Tray and application exit (M5)

The Windows supervisor owns one system tray icon. Its menu provides **打开 CommandDeck** and **退出 CommandDeck**; double-clicking the icon opens the workbench. Opening a minimized standalone workbench restores its existing window and Pi runtime. UI reload/replacement retains the supervisor's original tray. Closing the main window still exits the application; there is no close-to-tray setting or promise that tasks keep running after application exit.

Tray exit uses the same task drain and native-window restoration path as ordinary exit. If that path fails, the workbench and tray remain available with a notice; no automatic second exit or task replay is scheduled. The tray is destroyed after successful cleanup. Tray creation failure leaves ordinary window controls usable.

`npm run test:tray` runs the actual source supervisor/UI, minimizes and reopens the existing UI through its native menu callback, reloads it without repeating an offline probe, embeds/detaches the owned NO DSP fixture and requests normal exit through the tray handler. An external native observer checks the application's process group after exit. `test:workbench` additionally checks that UI-process replacement retains the original tray. The portable default/reopen check requires `desktopTray: 1`; candidate `4dbf1ea650f1b5767243898b52f77c9f4aaf4352` passed both actual starts outside the checkout, including host-driven restore/exit, retained closed history, zero observed packaged children after each exit and unchanged complete bundles. Each start makes two explicit offline probe requests. These tests do not establish physical taskbar input, restoring a minimized embedded game host, background rendering or sleep/wake behavior. A computer-use attempt on 2026-10-28 encountered the locked desktop and stopped before input.

The implementation follows Electron's [Tray API](https://www.electronjs.org/docs/latest/api/tray). No task or credential content is placed in the icon, tooltip or menu.

## Suspend and wake (M5)

Windows power events pause new task admission, invalidate the old research catalog and confirmation nonces, and cancel/drain managed work through the normal paths. Already submitted native work retains its original intent and may still return its receipt; suspension is not a native undo or an atomic stop. Existing bounded calls may finish. Cached telemetry is marked stale, and results from before the interruption cannot become fresh data again.
